# zenn

[zenn.dev/yusaka_lu](https://zenn.dev/yusaka_lu) に公開する記事。

手を動かして確かめたことを記事にする。読者が再現するためのコードは別リポジトリ [zenn-examples](https://github.com/y-sakamoto-lu-llc/zenn-examples) にあり、記事からは commit permalink で参照する。

記事の元になる調査・検証の記録は手元のナレッジベースにあり、ここには**公開する形に書き直したものだけ**を置く。

## 名乗り

プロフィールと Publication の紹介文は、`記事の規約` の「題材」と同じことを言う。**片方だけ直すとずれる**ので、変えるときは3つ並べて直す。反映先は zenn.dev の設定画面で、このリポジトリからは push できない。

**Publication は 2026-09-11 に見送りを決めた。** 申請していないので、下の紹介文はまだどこにも反映されていない。プロフィールだけが生きている。

再開するときのために決めたところまで残す。`name` は `lu_tech`、表示名は `合同会社Lu`。**`name` は変えられない。** 記事の URL が `zenn.dev/lu_tech/articles/<slug>` になり、変更すると公開済みの URL が全部切れる。領域を名前に入れなかったのは、看板を広げたときに URL が実態とずれるため（Rails 以外も扱う）。

プロフィール（bio）:

> 流通している話を最小構成で再現して、外れた分を書いています。題材は本番で動いている Ruby on Rails と、そこへの生成AI の入れ方です。バックエンドが10年、うち Rails が5年。合同会社Lu で受託開発と技術支援をしています。

Publication の紹介文:

> よく言われている話を、最小構成で作り直して測っています。当たっていた分と外れた分を、再現手順ごと置きます。題材は本番で動いている Ruby on Rails と、そこへの生成AI の入れ方です。福岡で受託開発と技術支援をしている会社です。

書き換えるときの制約が3つある。**会社サイトの URL を本文に書かない**（`website_url` が別に持つので二重に出る）。**職能を中黒で並べない**。**謙譲語を使わない**。後ろの2つは 2026-09-11 の実測による。既存記事の本文1,159文のうち、抽象名詞を中黒で3つ並べた例は0件、「ご相談」の類は0件だった。

## 構成

```
articles/         記事本体。Zenn が読むのはここ直下の .md のみ
images/<slug>/    記事ごとの画像
scripts/          記事のチェックに使うスクリプト
```

`articles/` のサブディレクトリは Zenn に無視される。記事は必ず直下にフラットに置く。

図は **Mermaid** で書き、画像・SVG は貼らない（差分が追えず、あとで直せない）。`images/` に置くのは、スクリーンショットなど Mermaid で描けないものだけ。

## 執筆

```sh
mise install          # node を固定バージョンで入れる
npm ci                # 依存を lock 通りに入れる
npm run preview       # localhost:8000 でプレビュー
npm run new:article   # 記事の雛形を作る
npm run check:mermaid # 記事内の Mermaid を構文チェック
npm run check:title   # タイトルの署名が直近2本と重なっていないか
npm run check:topic   # topics の先頭と Publication への紐づけ
npm run stats         # 公開後の到達を数で見る
```

`main` に push すると Zenn へ自動デプロイされる。`published: false` の記事は下書き扱いで公開されない。


### プレビューの Mermaid は当てにならない

**Zenn の Mermaid は zenn-cli が描画しているのではない。** `https://embed.zenn.studio/mermaid` への iframe に委託されていて、図そのものは外部から返ってくる。そのため同じ記事・同じバージョンでも読み込むたびに「正常に描画される」「極小に潰れて読めない」「空白のまま」が入れ替わる（zenn-cli 0.5.2 と 0.5.3 で同じ挙動を確認、2026-08-28）。**バージョンを上げても直らない。** 潰れやすいのは `subgraph` を含む図。

構文の判定は `npm run check:mermaid` で行う。`mermaid.parse()` に通すだけで描画はしない。引数にファイルを渡せば個別に確認できる。図の**見た目**の最終確認は本番デプロイ後になる、と割り切る。

## 記事の規約

規約の総量に上限を置く。**この節と `CLAUDE.md` の合計を160行以内に保つ。** 超えるなら何かを消してから足す。これは体裁の話ではない。規約に書いた形はそのまま出力に転写されるので、規約が長いほど、それに従った均質な記事が出る。

同じ理由で、**この節では形を例示しない。** 埋める枠を与えると全記事がその枠の形になる。書くのは制約だけにする。

### 題材

**看板は「本番の Rails を、生成AI でどう扱うかを実測で判定する」。** `topics` の先頭は `rails` にし、生成AI 側の語は2番目以降へ置く。判定は `npm run check:topic`。

一覧とトピックフィードで最初に読まれるのは先頭のトピックで、そこが揃っていない記事は別の書き手として並ぶ。

混んでいる側を主語にしない。2026-09-11 の実測では、Rails トピックの直近1,200本が21か月分だったのに対し、Claude Code トピックの1,200本は1か月分だった。後者の個人記事はいいね中央値0、半数が0いいね。交差点（Rails のトピックでタイトルに生成AI 系の語を持つ記事）は21か月で50本、個人に限れば25本しかない。

**題材が交差点に落ちているかは機械で判定できない。** 書き始める前に1問。

> この記事は、Rails を本番で使っている人が、生成AI をどう扱うかを決めるときに使えるか。

使えないなら、題材ではなく看板のほうを疑う。看板を変えるのは記事1本の判断ではない。

### タイトル

**70字以内。** 超えると Zenn Editor が弾く。

1つの命題か1つの問いにする。読者が得るものを名指しできないなら、記事の焦点がまだ絞れていない。

**署名を直近2本と変える。** 署名は区切り記号と文末の組み合わせ。判定は `npm run check:title` が持つ。一覧に並んだとき、記事ごとの差より書式の一致のほうが目立つと、中身を読む前に量産物として処理される。2026-08 までの7本は7本とも `—` の2部構成だった。

**3案出してから選ぶ。** 署名の異なる形で3つ書き、検査に落ちたものを外して残りから選ぶ。1案目に飛びつくと前に書いた記事の形をなぞる。採用しなかった2案は完了報告に残す。

発想の足場として、これまでに書けている形を4つ挙げる。**選択肢の列挙であって、埋める枠ではない。**

| 形 | 何を置くか |
| --- | --- |
| 断定 | 結論の命題そのもの |
| 問い | 答えではなく問いを置く |
| 数値 | 測った結果の数字を1つ |
| 成果物 | 読者が手に入れるもの |

数字は入れられるなら入れる（範囲が有限だと分かると読み始めのコストが下がる）。必須ではない。**タイトルの形と骨格の型を対応させない。** 対応させると、記事の大半を占める型がタイトルの形も占めることになる。

### 骨格

**型は読者の状態で決まる。** 書き手が何を持っているかではない。同じ検証結果でも、読者が困っているのか、選ぼうとしているのか、作ろうとしているのかで別の記事になる。**1本に2つ以上の型を混ぜない。**

| 型 | 読者の状態 | 記事に要るもの | 実績 |
| --- | --- | --- | --- |
| 検証レポート | 採用するか迷っている | 数値と、試していないことの線引き | 5本 |
| チュートリアル | ゼロから作りたい | 最後まで動く最小構成 | 1本 |
| つまずき解決 | エラーで止まっている | 再現手順と直った証拠 | **0本・未検証** |
| 設計の主張 | やり方は知っていて納得したい | 反証条件 | **0本・未検証** |

実績0本の2つは、この型で書けるという仮説であって実測ではない。

どの型でも置くものと、その順序。

1. リード
2. `## この記事で書くこと・書かないこと`
3. `## 検証環境` — 表。検証日を最終行に
4. `## 結論` — スクロールなしで見える位置に
5. 本文
6. `## 自分では確かめていないこと` — **`##` で立てる。`###` に落とすと長い記事では埋没し、断定したのと同じになる**
7. `## まとめ`
8. `## 参考` — リンクごとに、そのリンクが何を言っているかを1行

2・3・4 は読者が1画面目で離脱するかどうかを決める場所で、あとから足す装飾ではない。

型ごとの差が出るのは本文（5）だけ。

- **検証レポート** — 観点ごとに `##`。羅列で終わらせず、共通の結論を最後に置く
- **チュートリアル** — 「そこまでで一度動く」単位で `##` を切る。動かない中間状態をまたぐ切り方は間違っている
- **つまずき解決** — エラーメッセージを原文のままリードに置く。読者は検索窓にそれを貼って来るので、意訳すると届かない
- **設計の主張** — 判断軸を並べて結論に収束させる。「Aは間違い、Bが正しい」ではなく「この軸ではA、この軸ではB」

**本文の `##` に番号を振るかは記事ごとに決める。3本続けて番号付きにしない。** 2026-08 までの7本のうち5本が番号付きで、これは規約に番号付きの見出しが例示されていたことの転写だった。

### 長さ

**観点は書き始める前に数える。書いている途中で増えたら、増やすのではなく落とす。** 落とした観点は `## 自分では確かめていないこと` か `## この記事で書かないこと` に1行で退避する。

**分割して次回に回さない。** 先に分割を宣言した連載は、これまで1本の例外もなく止まっている。長さの打ち手は捨てることであって、割ることではない。

節の数に上限は置かない（`##` が18個で主張が1つの記事がある）。**1つの `##` が2,500字を超えたら、その節が記事の主題になっていないか疑う。** 網羅しようとすると、公式ドキュメントに書いていないこと（自分の環境で起きたこと、選んだ理由、踏んだ罠）が薄まる。記事の価値はそこにしかない。

### コードと出力

- コードブロックの前に1行「何のコードか」、後ろに1〜2行「どこを見るか」。裸のコードブロックは読み飛ばされる
- エラーと実行結果は原文のまま貼る。読者は自分の画面と1文字ずつ突き合わせる
- 全文を貼らない。変えた部分とその前後だけ。全文が要るならリポジトリへリンクする
- 失敗版を見せてから直す。完成形だけ出すと、読者は自分の失敗と記事のどこが違うのか照合できない
- コードフェンスにファイル名を書く（`` ```ruby:config/application.rb ``）

### slug

**12〜50文字**、`a-z` `0-9` `-` `_` のみ。内容が分かる名前にする。`zenn-examples` 側のディレクトリ名と揃える。

### frontmatter

```yaml
---
title: 日本語のタイトル
emoji: "🚂"
type: tech
topics: [rails, ruby, sqlite]
published: false
---
```

**Publication は見送り中なので `publication_name` を書かない**（「名乗り」を見る）。再開して申請が通ったら、frontmatter にこのキーを足し、`scripts/topic-check.mjs` の `PUBLICATION` に `lu_tech` を入れる。埋めた時点で全記事が検査対象になる。

Zenn が解釈しないキーは書かない。元にした手元の記録との対応は、記録側に持つ。

### 検証環境ブロック

表には OS・言語・フレームワーク・検証対象のバージョンを並べる。読者が「自分の環境で再現できるか」を最初に判断できるようにするため。表の直後に再現用コードへのリンクを置く。

```markdown
コードは [zenn-examples/<slug>](https://github.com/y-sakamoto-lu-llc/zenn-examples/tree/<commit>/<slug>) にあります。
```

## 運用上の注意

- **`main` への push は公開記事の書き換えと同義**（Zenn が自動デプロイする）。force push は禁止設定にしてある
- Zenn Connect の GitHub App は**このリポジトリだけ**に許可する（`Only select repositories`）
- GitHub Actions は置かない。CI を入れる場合は `pull_request_target` を使わず、既定の権限を read-only にする
- 記事を消すときは Zenn ダッシュボードでの削除が必要。ファイルを消すだけでは次のデプロイで復活する
